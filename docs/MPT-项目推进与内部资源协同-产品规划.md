# MPT项目推进与内部资源协同：用户旅程及产品规划

日期：2026-11-01。范围：产品规划与Pencil原型；不实施应用接口或业务代码。COME3.0按用户确认只做Mock。员工及工号均为示例，不代表真实员工或实际可用资源。

## 1. 两条入口，一条持续推进闭环

### 从未完成MPT评估

是否进入评估取决于有没有完成过评估，而不是CRM记录创建日期。历史很久的商机如从未评估，也走首次评估；刚创建但已有有效评估的项目可直接进入画像对话。

P10.48开始评估→M自评及阶段专项追问→本维度结果→修改或保存→P自评/核对/结果→T独立评估/结果→形成当前画像。未完成时可恢复进度，不把已暂存答案当作完整画像。

Agent读取已知资料后问关键缺口，不能把完整问卷机械重问一遍。选项用于帮助销售表达事实，阶段判断需要结合实际条件。每轮优先1—3问，已知不重复问，未知可保留。

### 已有画像

默认进入P10.42。第一屏让销售看到：当前位置、当前事实、关键卡点、最新关联数据与最有价值的下一问题。

用户可直接描述会后新进展或请求推进建议。系统结合项目画像、CRM实体、历史沟通和必要外部信息，完成：

1. 判断现状与阶段是否仍成立。
2. 找出影响下一里程碑的缺口。
3. 生成最多8项、默认优先3项的可执行行动。
4. 标出哪些行动需要内部资源及适用条件。
5. 选择同事→打开对应COME3.0会话草稿。
6. 沟通后记录真实结果，更新项目画像或形成待确认阶段变更。

发生主体变更、重招或重大证据冲突时，提示复核受影响维度，避免无依据重启全部评估。用户可随时重新评估或补充信息。

## 2. P10.42的工作区结构

左侧保留当前项目会话历史和全局导航。中间为主要对话区，右侧为画像与本轮数据。

中间的轻量入口为对话推进、阶段分析、推进方案、资源支持。它们围绕同一项目上下文，不创建互不相关的聊天或丢失已确认信息。

默认回答呈现：一句当前判断→最重要的原因→2—3项行动→关键追问。以精炼可执行内容为主，不在回答正文堆全部证据。

右侧常驻：

- M:P当前坐标和T独立采购状态。
- 查看项目画像，进入P10.43矩阵。
- 已确认、推进中、待补充的核心事实。
- 本轮实际关联的商机、进展、联系人及商务活动卡片。
- 外部信息的检索/待核状态。
- 重新评估与补充入口。

不是每次请求都重新查全库。按问题检索实体与字段，保留实际使用的来源清单；查询失败或数据未找到要明确表达，不能补造。

## 3. 阶段分析

### 输入

- 当前有效M/P/T、各自申报/核验状态、主体及采购范围。
- 画像事实、缺口、原始口述与历史版本。
- 当前客户、联系人及内部组织/决策链。
- 当前线索或商机、对应进展、商务活动、会议和待办。
- 用户本轮真实补充、意图与近期目标。
- 按需取得的公开信息及其来源、日期、主体匹配与有效性。

所有数据绑定entity_type+entity_id，不能只按客户名拼接不同项目。联系人及内部资源也需区分“客户联系人”与“公司内部同事”。

### 分析流程

1. 明确本轮要支持的判断：阶段、推进、风险、资源或会后更新。
2. 对照当前M/P/T定义检查条件、来源与反证。
3. 将缺口分为：业务条件未满足、事实未知、证据冲突、主体/范围失效。
4. 优先追问能改变结论的缺口；普通追问未结束前不提前显示完成结论。
5. 形成当前阶段判断、关键阻塞、可推进路径及仍未知事项。
6. 若建议变更，独立展示原值/建议值/理由/影响，用户确认后保存为申报；管理核验另行完成。

外部新闻不能单独证明客户审批或融资完成。公开渠道与同名项目必须核对，投资机构新闻只能形成待核资源线索，不能认定其愿意投资本项目。

## 4. 下一步方案生成

方案是矩阵格策略、M缺口、P突破、T窗口及内部资源的组合，不是通用销售话术。

每个行动至少包含：要获得的业务结果、执行对象、建议责任人、时间或待确认节点、关闭标准、所需资料、可用支持与依赖。时间未知不编造已承诺日期，内部同事未接单不直接写为已分配。

### 三类输出

- 定方向：本次先解决什么、目标M/P是什么、何种情况下应控投或停止。
- 识风险：未满足条件及可能后果，是否影响阶段、采购窗口、合同/融资或资源投入。
- 递资源：哪一项行动需要谁支持、为何匹配、需准备什么、哪些条件需审批或本人确认。

### 计划与创建分开

生成推进方案、整理下一步、准备商务活动等入口先生成分析或计划。只有明确“创建任务/活动/进展草稿”的建议，点击后才进入可编辑表单并经确认写入CRM。方案不能直接触发报价、投资承诺、排产或对外发送。

行动结果从CRM实际进展或销售确认回流画像。创建了任务不等于任务完成，联系了同事不等于资源落实。

## 5. 各M阶段可寻求的支持

以下是待企业资源目录配置的产品分类，不表示公司已经具备全部资源。

- M0规划：区域/市场研究、开发路径讨论、基础技术交流、项目核真；先确认项目意图、主体和开发动作。
- M1开发：并网接口与技术输入、许可适用事项协调、土地/现场技术边界、EPC或本地顾问渠道；以核卡点和输入资料为先。
- M2核心RTB：转售与承继核验、设备方案及经济性、投资团队初筛、未来业主认可；不能把核心RTB等同融资关闭。
- M3投资级RTB推进：供应链金融初筛、投资渠道协同、Bankability和经济性复核、EPC预算、收入/消纳路径支持。
- M4开工准备：NTP/CP清单、合同与付款担保协调、供应链交付窗口、现场接口；排产和资源承诺按授权审批。
- M5建设：交付、现场工程、性能与质保、验收回款、真实变更与补供范围；增容二期必要时建立新项目范围。

P维度补充：P0/P1可匹配公开渠道研究、公司介绍与拜访准备；P2/P3可匹配技术/行业专家参加沟通、接待及决策链信息整理；P4/P5可匹配商务、法务、投标、交付与批准条件支持。不能把同事既往项目交集推断为私人关系或实际影响力。

T维度补充：RFI准备能力材料；RFQ确认预算用途与报价输入；RFP进行投标与技术商务评审；T4组织澄清和谈判支持；T5核定标、生效与履约交接。采购轮次与设备范围独立保存，PPA/收入事件另存。

## 6. M3开发商融资缺口示例

P10.98使用独立示例项目Helios Development / OP-DEMO-RTB01，不把它当作Coventry项目的新事实。

已知：客户形成商业可行性分析、开发经验有限、尚无合适投资渠道。商业分析是客户提供的材料，不自动等于内部独立核验或融资可行性获批。

Agent先问：资金规模/用途是什么、希望股权还是债权支持、融资窗口和可提供材料是什么。必要时继续核项目权利、批准文件、收入结构、SPV/股权、未来采购主体及承继条件。

建议路径：

1. 整理可供内部初筛的融资需求包。
2. 请供应链金融同事确认支持范围及所需资料。
3. 如适用，再请投资渠道同事调研候选机构偏好。
4. 如商业分析输入不足，请经济性同事协助复核假设。
5. 获取同事真实反馈后确定下一节点；更新项目融资条件，而非直接宣告进入M4。

## 7. 内部资源目录与同事卡片

资源条目建议包含：资源ID、分类、可支持事项、适用M/P/T、国家/市场/技术范围、申请条件、必需输入、不可承诺事项、负责部门、员工引用、审批路径、有效期/更新时间及状态。

员工目录至少包含：稳定员工ID、姓名、工号、部门、岗位、专业领域、区域范围、联系路由及可见权限。是否可接单、可投入时间及交付节点需本人确认，不能由LLM推断。

匹配时先按权限、市场/事项、阶段及硬性条件过滤，再按专业匹配度、已有授权项目交集和目录有效性排序；解释匹配原因，不生成伪精确分数。无合适资源就说明未匹配并建议目录负责人确认。

卡片展示：姓名、工号、部门/岗位、可支持事项、COME3.0入口。点击卡片或入口，打开对应员工会话；不同同事必须使用各自员工ID，不统一跳到同一个人。

原型示例：

- 周予安 / MOCK-FIN-021 / 集团供应链金融：融资需求初筛、支持路径调研、跨部门协同。
- 林知远 / MOCK-INV-008 / 战略投资及投资者关系：投资偏好与候选渠道匹配。
- 陈嘉宁 / MOCK-TECH-032 / 储能经济性分析：收益假设、设备方案与敏感性输入复核。
- 顾文博 / MOCK-ENG-017 / 电网接入专家：并网接口及资料缺口梳理。

上述均非真实员工，不应回写正式员工目录。资源卡不表示已经获得资金、审批或同事承诺。

## 8. COME3.0交互与材料准备

用户确认存在接口，但本次不接入。P10.100、102、103、104分别展示四名同事的独立会话Mock。

点击员工卡片→按员工ID定位会话→带入可编辑沟通摘要→用户选择资料与发送。仅打开会话不发送消息。默认不携带全部CRM记录、客户联系人和财务附件；资料范围由用户选择并服从现有权限。

草稿建议包含：项目标识、当前阶段、当前卡点、希望同事支持什么、已有材料、希望确认的下一节点。避免把资源建议写成“公司已承诺提供融资”。

若未来接口失败，产品应给出可复制沟通摘要及员工信息，保留未发送草稿；不得静默标记已联系。真正发送授权、接口鉴权和消息回执属于后续开发范围。

## 9. 画像更新和共享

共享项目画像保存管理位置、主体/范围、事实、采购事件、变更历史；用户项目记忆保留该用户观察、关注点与未核实线索。系统prompt、Agent建议及资源匹配结果不能自动当成客户事实。

普通补充记录为相应来源/口述；阶段变动采用待确认建议。保存前展示前后值及依据，处理版本冲突；不能用过期会话覆盖更新画像。

内部协同结果另记为资源请求/任务：待准备、待联系、已联系、待确认、支持中、已完成/不适用。后续需要CRM进展或任务写入时走原有确认流程。

## 10. 矩阵表现和动效

P10.43保留M横轴、P纵轴，T在底部独立采购链展示。每个格子只留简短业务含义。图例用实色块明确六类背景：观察、培育、重点投入、冲刺/履约、风险控投、高危复核。

当前位置高亮，建议M方向和P方向分别标注。两条流动箭头指向建议目标，不画成项目已发生的轨迹。规则待补等信息移入设计规则，不以大段文字占据矩阵；需要专项复核的格子保留简短业务状态。

本次在Pen中使用相对路径mpt-portrait/advance-flow.glsl作为shader fill，@time驱动箭头流动。随.pen一起保存此依赖文件；PNG仅为静态快照。后续应用应支持暂停/减少动态效果，目标不能只靠动画或颜色表达。

## 12. 后续开发对象和验收

建议新增StageAnalysis、AdvancementPlan、ResourceCatalogItem、EmployeeRef、ResourceMatch、CollaborationDraft、PortraitChangeProposal；使用现有CRM实体引用与MPT事件/事实结构，不重建一套客户数据库。

分析结果必须关联画像版本及实际来源；计划目标区分M/P/T，行动有关闭标准；资源条目有适用条件与员工引用；沟通草稿关联选中员工，不存硬编码姓名路由。

验收至少覆盖：

- 未评估老商机仍进入评估；已有画像的新项目可直接对话。
- 恢复半途评估不重置已有回答。
- 内部数据不足、外部检索无结果时不编造依据。
- 并网受理不等于批准；投资渠道未落实不等于融资完成。
- 生成方案不创建任务；创建草稿须可编辑并确认。
- 不同员工卡打开对应会话；打开不发送，失败不记已联系。
- 未匹配到适用资源时不强行推荐。
- 主体变化、重招、过期证据及画像版本冲突可复核。
- 动效不改变管理位置；减少动效时仍能识别方向及目标。

本次没有实现以上服务、接口和权限逻辑，也没有发送真实IM消息；原型元数据仅表达设计意图。
