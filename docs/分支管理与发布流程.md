# 分支管理与发布流程

自2026-10-28起，Sales Buddy使用GitHub仓库管理代码、知识库和原型。

仓库：https://github.com/YunhaoPeter/Sales-Buddy

## 分支

- `main`：稳定版本，首次上传作为基线；之后通过发布PR更新。
- `develop`：已验证功能的集成分支。
- `codex/<任务名>`：本助手每次迭代使用的独立分支，从最新develop建立。
- 人工开发可使用 `feature/<功能>`、`fix/<问题>` 或 `docs/<主题>`。

不要直接在main或develop上实现日常修改，不强推共享分支。根目录AGENTS.md为后续助手保留此约定。

## 一次迭代

```sh
git fetch origin
git switch develop
git pull --ff-only origin develop
git switch -c codex/your-task
# 修改、验证、更新文档
git add <明确的文件>
npm run security:check
git commit -m "feat: describe the change"
git push -u origin codex/your-task
```

向develop创建PR，说明变更行为、验证结果和配置或数据影响。合并功能后，按版本批次从develop向main提交发布PR。需要可追溯发布时再创建版本标签，避免给未发布的基线误标正式版本。

初次导入空仓库允许直接建立main，随后建立同一提交的develop。上传完成后本地停留develop；下一次实施前新建任务分支。

## 验证层级

GitHub Actions在main、develop及任务分支推送和PR时运行密钥检查、可移植测试和生产构建。CI不需要真实模型或Exa密钥。

`npm run test:ci`运行可移植测试，明确排除依赖本地Artifact运行时的meetings.test.ts。它不代替完整P11导出和渲染验收。完整 `npm test` 与 `npm run test:e2e` 在配置相应运行时的本机执行。在线验证单独执行，可能消耗API额度。

## 仓库边界

纳入应用源码、测试、知识库、预制PPT及预览、规划文档、原始Pencil文件和HTML设计参考。数据库、API密钥、用户对话与记忆、用户上传与生成文件、调试输出、自动测试报告和运行截图留在本地。

Pencil源文件保存在designs/，应用从仓库根目录启动。首次导入复制自原工作区，原工作区文件保留。后续改原型时同步更新仓库内的版本。

`security:check`扫描暂存区；CI用 `--tracked` 扫描跟踪文件。它会检查常见令牌格式，并与本地.env中的实际模型和Exa密钥比对，不输出密钥。该检查不替代GitHub Secret Scanning。

当前仓库提交的是协作流程和CI配置，不代表已启用GitHub服务端的强制分支保护。仓库所有者可在GitHub Rulesets中为main/develop要求PR、禁止删除和强推，并在首轮CI成功后添加对应状态检查。
